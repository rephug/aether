**Date:** September 12, 2026
**Context:** Phase WF (The Companion), imported by the Run 0 docs PR (#150). Decisions are numbered as in `docs/roadmap/phase_wf_the_companion.md`; each stage that ships appends its decision here.

## New decisions

### 121. Mock provider confidence 0.1 + `[MOCK]` prefix; `/scan` batches 10 symbols per turn grouped by file

**Date:** 2026-09-12
**Status:** ✅ Implemented (Stage WF.0)

**Context:** New users needed a Gemini key for the initial scan pass before the Claude Code Max enrichment workflow could take over. The spec assumed a key-free mock inference provider already existed with confidence 1.0; the tree had none (`--inference-provider mock` was rejected by the CLI), so WF.0 adds one.

**Decision:** `inference.provider = "mock"` (`InferenceProviderKind::Mock`, `MockInferenceProvider` in `aether-infer`) writes a placeholder SIR per symbol from tree-sitter facts only: intent prefixed `[MOCK]`, empty lists, confidence `MOCK_SIR_CONFIDENCE = 0.1`. The low confidence makes `aether_audit_candidates` rank unscanned symbols first. `/scan <crate> [batch-size]` (`.claude/commands/scan.md`) replaces placeholders 10 symbols per reasoning turn, grouped by source file, targeting confidence 0.7–0.8 with no reasoning traces and no `aether_sir_context` calls; `scripts/scan_all.sh` runs up to 4 `claude -p "/scan <crate>"` sessions in parallel over every workspace member (from `cargo metadata`, or the directories under `crates/`; a root package is scoped to its own targets' `src/`, `tests/`, `benches/` directories, never the whole workspace) and reports before/after target counts. The onboarding index is `aetherd --index-once --full --inference-provider mock`: without `--full` the daemon only builds the structural index and writes no SIRs. Both assets are generated by `aetherd init-agent --platform claude` so downstream projects get the same flow; the AETHER checkout keeps copies that a test holds byte-identical to the templates. Deepening afterwards uses `aetherd regenerate --deep` (no `enrich_all.sh` ships in the repo). `AETHER_AGENT_SCHEMA_VERSION` 3 → 4 because the CLAUDE.md template gained the Zero-Gemini Onboarding section.

### 111. Workflow slash commands are generated by `init-agent`

**Date:** 2026-10-14
**Status:** ✅ Implemented (Stage WF.1)

**Context:** The audit and refactor commands already came from `init-agent` templates (`crates/aetherd/src/templates/*_cmd.rs`), and the AETHER checkout tracks the generated copies under `.claude/commands/` with a test holding them byte-identical. Hand-written workflow commands would drift from the tool surface the same way untracked ones did before.

**Decision:** `/pre-flight`, `/review`, `/explain-area` and `/impact` are four more templates (`PreFlightCommandTemplate`, `ReviewCommandTemplate`, `ExplainAreaCommandTemplate`, `ImpactCommandTemplate`), written to `.claude/commands/*.md` by `aetherd init-agent --platform claude` (and `all`). The AETHER checkout tracks the generated files, and `checked_in_commands_match_templates` covers them.

### 112. Slash commands are static templates

**Date:** 2026-10-14
**Status:** ✅ Implemented (Stage WF.1)

**Context:** A command could be rendered per project (crate names, enabled tools, provider), but every value it would need is cheaper and fresher to look up at run time through the MCP tools, and project-specific text would make the tracked copies differ between workspaces. The spec's register calls these "read-only templates"; `/review` can write SIRs, so "static" is the property all four share.

**Decision:** The four templates ignore `TemplateContext` and render the same text everywhere. They name only tools that exist in `aether-mcp`'s router, with the request fields those tools accept (ids rather than names wherever a name could be ambiguous), and tell the agent to skip a step when an optional tool family (contracts) is unavailable. `/pre-flight`, `/explain-area` and `/impact` don't edit files or inject SIRs (like any `aether_get_sir` call, looking up a symbol that has no SIR yet queues it for the daemon); `/review` writes nothing unless the user agrees to the SIR updates it proposes, and then passes the full field set and the `source_hash` it read. None of them calls `aether_refactor_prep`, which runs the configured inference provider. Hybrid `aether_search` does embed its query with the configured embeddings provider, so the commands use lexical mode for exact names and hybrid only for concepts.

### 113. Recommended workflow: /explain-area → /pre-flight → implement → /review

**Date:** 2026-10-14
**Status:** ✅ Implemented (Stage WF.1)

**Context:** The spec's register calls this the four-command workflow "pre-flight → implement → review"; its WF.1 text adds `/explain-area` in front and `/impact` as a pre-change check.

**Decision:** The CLAUDE.md template gains a "Slash Commands" section listing every generated command and recommending `/explain-area` (unfamiliar area) → `/pre-flight <task>` → implement → `/review`, with `/impact <symbol>` before changing a widely used symbol. `/review` compares the branch against the pre-change SIRs (using `aether_why_changed` when the daemon has already regenerated one), its callers, and the active contract clauses, which the agent judges against the new code. `aether_contract_check` and `aether_verify_intent` (which needs a `/refactor` or `/refactor-deep` snapshot) compare stored SIRs, so they count only as a second opinion until the branch's SIRs are refreshed. The section is appended after "Verify Commands", so the template's long format string is untouched. `AETHER_AGENT_SCHEMA_VERSION` 4 → 5 because the CLAUDE.md template changed.

### 114. Slash command files follow Claude Code's command format

**Date:** 2026-10-14
**Status:** ✅ Implemented (Stage WF.1)

**Context:** Claude Code reads project commands from `.claude/commands/<name>.md`, with optional YAML front matter (`description`, `argument-hint`) and `$ARGUMENTS` substituted with whatever follows the command.

**Decision:** Each template starts with front matter giving `description` and, where the command takes input, `argument-hint` (`<task description>`, `[base-branch]`, `<file, directory, crate or symbol>`, `<symbol>`), then a numbered, step-by-step body that ends with the exact shape of the answer, like the existing audit commands. File names are the command names: `pre-flight.md`, `review.md`, `explain-area.md`, `impact.md`.

### 115. `/context` output is self-contained, with no AETHER jargon

**Date:** 2026-10-14
**Status:** ✅ Implemented (Stage WF.1b)

**Context:** `/context` exists so that an assistant without MCP access (a web chat, another vendor's model) can work on part of the codebase. Anything in the pasted text that points at tools, ids or AETHER concepts is noise to that reader, and a hallucination risk.

**Decision:** `/context <target>` (`ContextCommandTemplate`, `.claude/commands/context.md`) gathers with the same tools as `/explain-area` plus `aether_test_intents` and the crate health tools, then writes one Markdown document in a fixed order: purpose, key components, how it works, dependencies, guarantees and edge cases, known weak spots, key code (30 lines at most), about 1,500 words at most. The template's rules ban references to tools, slash commands or the conversation, AETHER vocabulary ("SIR", "symbol id", "confidence", "generation pass", "health score", "blast radius", "AETHER"), `aether_*` names and internal ids or hashes, and say what to write instead. A banned word that is the project's own name or an identifier in its code is kept as the code spells it, so the command also works on AETHER itself or on code with a `confidence` field. Inferred statements are marked "(inferred)". The document is printed inside a four-backtick fence so its own code excerpts survive copying. The command doesn't edit files or inject SIRs. `aetherd context` (clipboard-ready export) remains the scripted counterpart.

### 116. `/health-check` caps at 5 worst crates and 3 recommendations

**Date:** 2026-10-14
**Status:** ✅ Implemented (Stage WF.1b)

**Context:** A session-start check is only useful if it is read every time, so it has to fit in about 30 seconds and say nothing when there is nothing to say. `aether_status` reports SIR coverage but not confidence, and no MCP tool summarizes SIR confidence.

**Decision:** `/health-check` (`HealthCheckCommandTemplate`, `.claude/commands/health-check.md`) calls `aether_status`, `aether_health_hotspots` (`limit` 5; it lists only crates scoring 75 or below, each with its top violation) and `aether_health` (cycles and risk hotspots, `limit` 5). Confidence comes from a SQL query on `.aether/meta.sqlite`, which `/next` and `/scan` also query directly, but opened read-only (`sqlite3 -readonly`, or Python's `sqlite3` with `mode=ro`): SIR count, average confidence, `[MOCK]` placeholders, other SIRs below 0.5 and deep SIRs, counting only non-empty rows with a symbol. The report has a fixed shape listing at most 5 crates and at most 3 one-line recommendations, each naming a command (`/scan`, `/enrich`, `/audit`, `/refactor`, `/next`). With coverage of at least 90%, no placeholders, average confidence of at least 0.7 and no crate in the hotspot list, it prints one "All healthy" line instead. A workspace with no indexed symbols (the MCP server creates an empty store on start, so `store_present` alone can't tell) gets a suggestion of the structural `aetherd --workspace . --index-once`, never a `--full` run that could call a paid provider. The CLAUDE.md template's Slash Commands section lists `/context` and `/health-check` and recommends `/health-check` at the start of a session; `AETHER_AGENT_SCHEMA_VERSION` 5 → 6 for that template change.

### 117. CI review is advisory and never blocks

**Date:** 2026-10-14
**Status:** ✅ Implemented (Stage WF.2)

**Context:** Structural signals (coupling, centrality, crate scores) are useful prompts for a reviewer but are not pass/fail facts about a pull request, and a slow or broken first build must not hold up merges.

**Decision:** The generated job sets `continue-on-error: true` (the workflow run stays green) and a 120-minute timeout, reports findings as neutral tables without a verdict, and skips the comment step where it cannot succeed (fork PRs). The job's own check can still fail, for example on a failed build, so the workflow header and `docs/CI_SETUP.md` say not to make it a required status check.

### 118. No SIR generation in CI by default

**Date:** 2026-10-14
**Status:** ✅ Implemented (Stage WF.2)

**Context:** SIR generation needs an inference provider, which means API keys in CI secrets, per-push cost, and source code leaving the runner.

**Decision:** The workflow indexes with `aetherd --workspace . --index-once --inference-provider mock` (no `--full`), so only the structural index is built, and is given no secrets. The report draws only on `mine-coupling`/`blast-radius`, `health` and `health-score`, leaves "no SIR" risk factors out because they would apply to every symbol, and says that the scores share a fixed offset in CI. SIR-powered review is described in `docs/CI_SETUP.md` as an opt-in a project can wire up itself.

### 119. One sticky PR comment, updated in place

**Date:** 2026-10-14
**Status:** ✅ Implemented (Stage WF.2)

**Context:** A new comment per push buries the conversation; third-party sticky-comment actions add a supply-chain dependency to every adopting repository.

**Decision:** The report starts with the hidden marker `<!-- aether-review -->` and names the commit it describes. The last step uses the runner's preinstalled `gh` CLI and the job's `GITHUB_TOKEN` (`pull-requests: write`) to find a comment by `github-actions[bot]` containing the marker and edit it, or create one. Steps run under `bash -eo pipefail`, so a failed listing fails the step instead of posting a duplicate. Runs are grouped per PR and queue rather than cancel, so a first `aetherd` build is never lost. Fork PRs get a read-only token, so the comment step is skipped for them; every pull-request run whose analysis finishes also writes the report to the job summary, which fork PRs can read. `pull_request_target` is deliberately not used. A section whose `aetherd` command failed says "Unavailable" rather than reporting nothing found.

### 120. The CI workflow is generated by `init-agent` for the Claude platform

**Date:** 2026-10-14
**Status:** ✅ Implemented (Stage WF.2)

**Context:** The workflow belongs in the repositories that adopt AETHER, not in AETHER's own CI, and AETHER publishes no release binaries yet. GitHub scopes caches saved by `pull_request` runs to that pull request, and `actions/cache` saves only when the whole job succeeds.

**Decision:** `aetherd init-agent --platform claude` (and `all`, the default platform) writes `.github/workflows/aether-review.yml` (`GithubReviewWorkflowTemplate`), skipped when the file exists unless `--force`. AETHER's own `.github/workflows` is unchanged. The workflow builds `aetherd` with `cargo install --locked --git https://github.com/rephug/aether --rev <commit>`, where the commit is `AETHER_REF` (default `main`; a SHA, branch or tag, resolved strictly with `git ls-remote`). The build is restored and saved with `actions/cache/restore` and `actions/cache/save`, the latter right after the build. Pull requests reuse any earlier build, even of an older AETHER commit, and build only when nothing is cached; a weekly schedule and `workflow_dispatch` rebuild for the current commit and seed the default branch's cache, which all pull requests can restore. Pinning `AETHER_REF` to a SHA makes runs reproducible. The checkout doesn't persist the job token, so the built tool can't read it from `.git/config`. When release binaries exist, a download should replace the build.
